# Agent Chat Mode Architecture

## State boundaries
- `raidStore` remains source of truth for raid orchestration and combat/task state.
- `chatStore` owns chat threads only (`agentId -> AgentChatThread`) and persists those threads to `localStorage`.
- No raid state is duplicated in chat state; UI passes a `ChatAgentUI` object into chat actions when needed.

## Prompt seeding
- Each agent thread starts with one system message generated by `buildAgentSystemPrompt(agent)`.
- Prompt includes name, role, personality, skills, responsibilities, and out-of-scope behavior.
- Role-specific defaults fill responsibilities/out-of-scope when agent-specific values are missing.

## Integration contract
- UI layer depends on `ChatAgentUI` and `ChatMessage` types, independent from transport details.
- API layer depends on `AgentChatApi` interface.
- `MockAgentChatApi` is the default implementation for local/dev-first behavior.
- `HttpAgentChatApi` is available for real backend wiring without changing store/UI contracts.
